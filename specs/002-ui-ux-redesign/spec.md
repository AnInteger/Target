# Feature Specification: UI/UX 全面重设计（原型先行）

**Feature Branch**: `002-ui-ux-redesign`

**Created**: 2026-08-18

**Status**: Complete 2026-08-22——六屏原型全部用户通过（今日 R4/列表 R2/编辑器 R1/回顾 R3/设置 R2/打卡反馈随今日屏）、SC-001…006 走查收口（design/reviews.md「实现审计」）；T028 品牌资产 2026-08-22 用户裁定 A 案「今日之环」并过生成链（图标/启动屏/iOS 18 深色变体），T033 同日用户确认侧载成功归档（T029 小组件 Swift 首编译随真机实证）——任务全勾、无遗留（真机看新图标需再手动触发一次构建侧载）；V4 决策动线与 V6 忙碌模式按 2026-08-21 用户裁决废止（记录见本文档与 reviews.md）

**Input**: User description: "我现在已经装好了这个软件，运行正常，但是对UI/UX还不是很满意。我想应该如何让你帮我设计一个好的原型设计，要有创意，懂需求，有设计感，是不得使用frontend-design？目前整个交互、设计都不是很满意，看看怎么一步一步完成一个更好的产品。"

## Clarifications

### Session 2026-08-18

- Q: 全面重设计后，目标还要不要区分"习惯类"和"里程碑类"两种类型？ → A: 合并为一种"目标"：不前置选类型，"是否一次性/有无截止日"作为创建流程中自然采集的属性；既有 kind 数据保留语义、零迁移。
- Q: iOS 小组件这次是只刷新视觉，还是顺带增强功能？ → A: 只视觉同步：小组件功能与数据流维持现状，仅外观刷成新设计语言（功能增强留作后续独立特性）。
- Q: 系统提醒通知要不要一起重设计？ → A: 一起重设计：通知文案统一到新品牌语气，且提醒时机与目标定义模型联动（提醒时机维度入选字段集后驱动每目标的提醒时刻）。
- Q: App 对外的正式名字叫什么？ → A: Target（沿用；图标、启动屏、桌面显示名与 TestFlight 展示名统一按此命名）。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 设计方向探索与原型系统 (Priority: P1)

作为产品所有者，我先看到若干个风格方向的"今日"屏高保真原型对比，选定方向后，得到一套完整的设计语言（色彩、字体、间距、图标、组件形态、动效规范）与全部核心屏的可评审原型。实现任何一屏之前，该屏原型必须先经过我评审通过。

**Why this priority**: 用户明确表示"整个交互、设计都不是很满意"，但未给出具体方向；在没有设计共识时直接改代码必然返工。原型先行是整个特性的地基，也是"一步一步完成更好的产品"的推进机制。

**Independent Test**: 原型无需开发环境即可在浏览器中查看；用户可逐屏给出"通过"或具体修改意见；设计语言有单一、明确的一致性来源。

**Acceptance Scenarios**:

1. **Given** 2–3 个风格方向的"今日"屏高保真原型，**When** 用户查看对比，**Then** 能选定一个方向（或指定融合调整），且该决策被记录
2. **Given** 已选定的设计方向，**When** 展开为核心屏原型（今日、目标列表、编辑器、周回顾、设置、打卡反馈），**Then** 每屏经过用户评审并获得明确"通过"
3. **Given** 任一核心屏原型未通过评审，**When** 用户提出修改意见，**Then** 原型在下一轮迭代中体现该意见并再次送审

---

### User Story 2 - 每日打卡动线重设计（今日视图 + 反馈仪式感） (Priority: P2)

晚上加班后打开 App，一眼看清今天还剩什么没做，两次交互内完成一次打卡，打卡瞬间获得温暖、有仪式感的反馈；当日全部目标达成时出现明确的成就时刻。今日视图要让"记录生活"的感觉取代"填 KPI 表"的感觉。

**Why this priority**: 每日打卡是产品最高频的路径，是"忙碌中找回生活感"这一核心价值的第一触点；此屏重设计完成后产品气质立刻改变。

**Independent Test**: 可通过原型走查与真机实测验证：打开 App → 总览 → 打卡 → 反馈全链路。

**Acceptance Scenarios**:

1. **Given** 3–5 个活跃目标，**When** 打开 App 进入今日视图，**Then** 不滚动即可总览全部目标的当日进度
2. **Given** 今日视图，**When** 点击任一目标的打卡操作，**Then** 两次交互内完成打卡且立即看到动效与文案反馈
3. **Given** 当日还剩最后一个目标未完成，**When** 完成最后一次打卡，**Then** 出现成就时刻（区别于普通打卡反馈）
4. **Given** 打卡反馈正在播放，**When** 用户连续快速打卡下一个目标，**Then** 反馈不阻塞、不错乱

---

### User Story 3 - 目标定义模型与创建流程重设计 (Priority: P3)

现状的问题（用户原话）："添加目标的界面感觉不好，目标不明确，只有名称、日期、图标"。重设计须回答"一个好的目标在这个产品里长什么样"：创建流程引导用户把模糊愿望变成明确目标——候选维度包括动机（为什么做）、成功标准（做成什么样算数）、提醒时机、关联场景等，具体字段集以原型方案为准；创建不再前置选择"习惯/里程碑"类型，一次性与截止日作为流程中自然回答的属性；编辑、暂停、归档获得一致的呈现与动线。

**Why this priority**: 目标定义的深度直接决定打卡、回顾等所有下游体验的成色，且是用户明确提出的功能级不满；但晚于打卡动线，因为存量目标的日常主要是打卡。

**Independent Test**: 在新 UI 下从零创建一个模板目标和一个自定义目标：产出目标比现状更明确（含选定的新维度），步数不多于现状。

**Acceptance Scenarios**:

1. **Given** 2–3 个目标定义模型候选方案的原型（字段集 + 创建动线），**When** 用户评审，**Then** 选定一个作为实现基准
2. **Given** 选定的模型，**When** 用户经模板路径创建目标，**Then** 步数不多于现状且产出目标包含选定的新维度（如动机/成功标准）
3. **Given** 自定义路径，**When** 输入模糊目标名，**Then** SMART 建议以新设计的语言内联呈现且可一键采用
4. **Given** 既有目标数据（无新维度字段），**When** 升级到新模型，**Then** 旧目标自动迁移呈现、无丢失，新维度可渐进补全

---

### User Story 4 - 回顾与调整流程重设计 (Priority: P4)

周一的周回顾获得与新语言一致的升级：数据被翻译成生活语言与图形（节奏条/走势/观察语），而不是工程报表。2026-08-21 用户裁决：回顾屏纯回看不控制下周（决策动线移除，调频/暂停走目标编辑器）、补签状态不上回顾屏、忙碌模式全 App 移除（今日屏长按补签功能保留）。

**Why this priority**: 周回顾是产品"教练"角色的载体，重要但频率为每周一次，排在日/创建路径之后。

**Independent Test**: 在新 UI 下完整走一遍周回顾（横滑逐目标查看节奏、走势与观察语），全 App 无忙碌模式残留入口与视觉。

**Acceptance Scenarios**:

1. **Given** 上周有打卡数据，**When** 用户打开周回顾，**Then** 每天一格的节奏条、近 4 周走势与一句观察语以图形化、生活化语言呈现，无纯表格观感，无完成率百分比（R2 语义转向）
2. **Given** 多个目标，**When** 用户左右滑动，**Then** 逐目标卡片逐一回看，指示点联动可点跳转（R2 裁决）；卡与页面无决策控件——要调整去目标编辑器（2026-08-21 R3 裁决）
3. **Given** 任意页面，**When** 浏览今日/目标/回顾/设置，**Then** 无忙碌模式的入口、徽标与降档文案（2026-08-21 裁决全 App 移除）

---

### User Story 5 - 设置、备份与系统级视觉收尾 (Priority: P5)

设置、备份导入导出、深色模式，以及（视范围决策）iOS 小组件/App 图标/启动屏的视觉同步，完成全 App 的一致性闭环。

**Why this priority**: 低频但决定"完成度"；范围中系统级元素（小组件/图标）的取舍取决于范围澄清结论。

**Independent Test**: 切换深色模式遍历全部屏幕核对可读性；在新 UI 下完成一次导出与导入。

**Acceptance Scenarios**:

1. **Given** 新设计语言，**When** 系统切换至深色模式，**Then** 全部屏幕文字与图形对比度达到可读标准
2. **Given** 新 UI 下的设置页，**When** 用户导出备份再导入覆盖，**Then** 流程可用且与现状结果等价
3. **Given** 范围决策包含小组件，**When** 查看 iOS 桌面/锁屏小组件，**Then** 其视觉与主 App 设计语言呼应
4. **Given** 已设定提醒时机的目标，**When** 到达该时刻，**Then** 收到的通知为新品牌语气文案，且时机与目标设定一致（真机验证）

### Edge Cases

- 活跃目标超过首屏容量（>5 个）时，今日视图如何组织（优先级排序、折叠或滚动策略）
- 连续快速打卡时反馈动效的叠加与打断处理
- 补签标记在补签日历中的视觉呈现不得与当日打卡混淆（回顾屏不展示补签状态，2026-08-21 裁决）
- 深色模式下目标颜色语义（区分度）是否仍然成立
- 主路径操作落在单手拇指热区内的可达性
- 空状态设计（无任何目标、周回顾无数据）
- 目标定义模型变化后，既有目标缺失新维度（如动机）时的兼容呈现与渐进补全
- 品牌升级后 App 图标/启动屏与主屏在浅色/深色系统外观下的适配
- 提醒时机字段为空或非法时的默认时段兜底，以及同档时段多目标的打扰合并（不因每目标时机不同而轰炸）
- 长名称目标、极端数字（0/99）在卡片与组件中的布局

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 遵循"原型先行"流程——任何一屏进入实现之前，该屏的高保真原型必须已获用户评审通过
- **FR-002**: 系统 MUST 建立统一的视觉设计语言（色彩、字体层级、间距、圆角、图标、组件形态、动效规范）作为单一一致性来源，并应用于全部屏幕；成品屏幕不得保留未加工的默认框架观感
- **FR-003**: 用户 MUST 能在打开 App 后两次交互内完成一次打卡；活跃目标不超过 5 个时，今日视图首屏无需滚动即可总览全部当日进度
- **FR-004**: 打卡完成 MUST 有即时、有仪式感的反馈（动效与文案）；当日全部目标达成时 MUST 呈现明确的成就时刻
- **FR-005**: 既有能力（目标管理、打卡、周回顾、补签、备份、通知、小组件）在新设计中 MUST 保留等价物；用户既有数据 MUST 零丢失，定义模型变化时自动迁移呈现（2026-08-21 用户裁决：忙碌模式自清单移除、全 App 裁撤——FR-007 功能级调整条款为凭，记录见 design/reviews.md 周回顾 R3 条目）
- **FR-006**: 新设计语言 MUST 同时提供浅色与深色两套呈现，正文文字对比度达到通用可读性标准
- **FR-007**: 重设计 MUST 为全面重设计：视觉、信息架构与导航、交互流程均可推翻重排，并允许必要的功能级调整；所有结构性/功能性调整以对应原型通过用户评审为前提
- **FR-008**: 视觉升级范围 MUST 为全套品牌升级：主 App 全部屏幕、iOS 桌面/锁屏小组件、App 图标与启动屏共用同一套设计语言；其中小组件仅做视觉同步，功能与数据流维持现状（功能增强为后续独立特性，不在本轮范围）
- **FR-009**: 设计风格基线 MUST 通过多方向对比确定：原型阶段先产出 2–3 个风格方向的"今日"屏对比原型，用户选定（或指定融合）后作为全套设计语言基线，该决策须有记录
- **FR-010**: 目标定义模型 MUST 深化重设计：创建目标不得止于名称/日期/图标，须让模糊愿望变成明确、可执行的目标（候选维度如：动机/为什么做、成功标准、提醒时机、与自己挂钩的场景等）；具体字段集在原型阶段以具体方案提出并经用户确认
- **FR-011**: 目标创建 MUST 采用单一"目标"概念：不前置选择类型；"是否一次性/有无截止日"在创建流程中作为属性自然采集（既有 kind 字段保留其语义作为该属性的存储，零迁移）；里程碑专属视图并入统一的 goal 呈现语言
- **FR-012**: 提醒通知 MUST 随本轮重设计：文案与语气统一到新品牌语言；提醒时机与目标定义模型联动——"提醒时机"维度入选最终字段集后，每目标的提醒时刻由该字段驱动（为空时回落默认时段，不重复打扰）

### Key Entities *(include if feature involves data)*

- **设计令牌（Design Token）**: 设计语言的单一来源——色彩板（浅/深两套）、字体与字号层级、间距与圆角与阴影刻度、动效时长与曲线、图标风格；全部屏幕与品牌素材只从这里取值
- **目标定义模型（Goal Definition Model）**: "一个目标包含什么"的字段集与语义（名称、频率之外的新维度，如动机、成功标准、提醒时机；类型不再前置分叉，"是否一次性/有截止日"为属性），含既有目标的迁移规则；具体字段集经原型评审确定
- **屏幕清单（Screen Inventory）**: 现有全部屏幕与状态（含空状态、忙碌态、深色态）的枚举，作为重设计范围与验收清单
- **原型评审记录**: 每屏对应的风格方向、评审轮次、用户意见与"通过"状态，用于跟踪推进与回归

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 全部核心屏（不少于 6 屏）的高保真原型均获用户明确"通过"，风格方向决策有记录
- **SC-002**: 真机/原型走查实测：打开 App 到完成一次打卡 ≤ 2 次交互
- **SC-003**: 既有 V1–V8 全部场景在新 UI 下回归通过，既有自动化测试全部通过
- **SC-004**: 成品屏幕 100% 取值于设计令牌，无硬编码样式、无默认框架素颜观感残留
- **SC-005**: 浅色与深色模式下正文对比度均达到通用可读性标准（不低于 WCAG AA 级别）
- **SC-006**: 按屏增量推进，任一时刻 App 内新旧风格并存的屏幕数不超过 1

## Assumptions

- 视觉、信息架构、交互流程不设限（可推翻重来）；功能与数据结构允许调整，但每项调整须先有通过评审的原型方案，且既有数据必须自动迁移、零丢失
- 产品形态不变：纯本地单用户应用，不引入账号体系与服务器端
- App 对外正式名称沿用 Target；桌面显示名、TestFlight 展示名与品牌素材（图标/启动屏）统一使用该名称
- 评审人即产品所有者本人（单用户产品），每屏默认预期一轮评审、至多两轮
- 高保真原型以"无需开发环境即可查看"的形式交付（浏览器可打开评审）
- 延续既有环境约束：iOS 真机为主要验收环境（经 CI 打包安装），Web 为本地全功能验证面并同步新视觉；品牌素材（图标/启动屏）在真机验收
- 每个迭代周期推进一至数屏（增量交付），不做一次性全量替换
- 既有快捷路径语义（如长按补签、Debug 时钟）在新 UI 下保留等价入口

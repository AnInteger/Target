# 功能规格：生活目标守护 iOS App（工作名 Target）

**Feature Branch**: `001-life-goal-tracker`

**Created**: 2026-08-17

**Status**: Draft

**Input**: User description: "我现在想开发一个目标管理的IOS APP。起因是我不在上班的过程中有很多想法，比如旅游、出去玩、健身、干自己的事情（比如做开发）的时候感觉状态很好，但是工作一段时间后，由于加班、精神高度集中，有些目标就被遗忘了，总想不起来，比如要好好吃饭，锻炼身体，注意健康等等。所以想设计一个APP用来解决这个问题，尽量帮助自己能在忙碌的工作中找到好好生活的感觉。看能不能参考下KPI、目标管理的专业领域支持，做一个极简但是有设计风格的APP"

## 问题与愿景

**问题**：上班族在闲暇时充满生活目标（旅行、出去玩、健身、做自己的项目），状态很好；但进入高强度工作期后，因为加班和精神高度集中，这些目标被逐渐遗忘——好好吃饭、锻炼身体、注意健康——忙碌中"好好生活的感觉"消失了。

**愿景**：一个极简、有设计感的 iOS 目标管理 App，借鉴 KPI / OKR / 习惯科学的专业方法，让忙碌的人在加班季也能持续"看见"、兑现自己的生活目标。

**专业方法映射（产品设计的领域依据）**：

| 专业概念 | 在本产品中的体现 |
| -------- | ---- |
| SMART / OKR（目标小而可衡量、数量聚焦） | 引导式建目标；活跃目标数量有上限 |
| 4DX 执行四原则：引领性指标 | 关注"每天的行为"（吃好饭、锻炼），而非滞后结果（体重） |
| 4DX：激励性记分表 | "今日"一屏看清所有目标状态，一眼知道自己过得好不好 |
| 4DX：规律问责节奏 | 每周一次轻量回顾，重新承诺或调整目标 |
| 习惯回路（线索-行为-奖励） | 提醒作为线索、一键打卡作为行为、进度与连击作为奖励 |
| 自我关怀的行为科学 | 忙碌期可降档（忙碌模式）或暂停目标，中断不清零羞辱，语气不指责 |

## Clarifications

### Session 2026-08-17

- Q: 习惯型目标每天可以打卡几次（如"好好吃饭"是否按三餐计 0/3）？ → A: 支持每日 1–N 次：目标可设"每日目标次数"，打卡按次累计（当日进度如 2/3），当日达到目标次数即视为完成；超额打卡计入累计次数，当日完成度以 100% 封顶
- Q: v1 是否包含数据备份能力（应对换机/重装丢数据）？ → A: 包含完整备份闭环：全部数据可导出为单个备份文件，并可在新设备/重装后导入恢复
- Q: 每周周期从哪天开始，周回顾何时生成与提醒？ → A: 周期定义为周一至周日；周一早晨自动结算上一周并生成周回顾，随当日晨间概要提醒用户参与
- Q: 修改进行中目标的频率从何时生效？ → A: 下一周期生效：进行中的周期仍按原频率结算，新频率自下周一启用（调整动作与周回顾节奏对齐）
- Q: 是否把桌面/锁屏小组件提升进 v1（不打开应用也能看见今日目标）？ → A: 是：v1 包含桌面与锁屏小组件，展示今日各目标状态与进度，点击单个目标可直接完成一次打卡，无需打开应用
- Q: 是否引入"生活电量"聚合指标作为首屏与小组件的视觉核心？ → A: 引入：生活电量（0–100%，由各活跃目标完成度加权合成的派生指标）作为首屏与小组件的视觉核心；连击等细节保留在目标层级；具体合成公式在规划阶段定义
- Q: 是否允许为过去日期补打卡（如昨天锻炼了但忘了记）？ → A: 允许：过去任意日期均可补签打卡，补签记录标记"补"并可撤销；补签计入对应日期的统计，周回顾如实呈现当期补签次数以保持透明
- Q: 是否在 v1 加入"忙碌模式"（加班周一键降档目标，周结算按降档口径，之后一键恢复）？ → A: 加入：可一键将所选或全部活跃习惯目标降至更低频率（当周生效、显式豁免"频率修改下一周期生效"的常规规则），当周结算按降档口径计算，结束一键恢复，今日视图与周回顾如实标注"忙碌模式"
- Q: "最多 5 个活跃目标"的上限是否包含里程碑型目标？ → A: 计入：习惯型与里程碑型共享 5 个活跃名额，聚焦原则对两类目标同样成立

### Session 2026-08-18

- Q: 开发环境为 WSL 且无 Mac（iOS 构建经 Codemagic），架构倾向 Flutter 跨平台——Android 是否在这个产品的视野内？ → A: Android 为 v1 后的明确计划：v1 仅发布 iOS，但架构须按跨平台约束设计（业务逻辑不与 iOS 专属能力耦合），Android 作为 v1 后第一个扩展目标写入假设
- Q: Flutter 架构下 v1 的桌面/锁屏小组件保留到什么程度？ → A: 完整保留：小组件仍可在桌面/锁屏直接完成一次打卡（FR-016/SC-007 口径不变）；实现上允许一块极小的平台原生扩展（不进入跨平台业务层），其构建与真机验证经 CI 完成
- Q: 用户自有 iPhone 且经 Codemagic 打包安装即可实机验证——本地（WSL）验证面选什么？ → A: Web 为本地验证主面且做到全功能：浏览器内真实持久化（刷新/重开不丢数据），导出/导入、补签、周回顾、忙碌模式等全部功能可在 Web 走查；提醒在页内模拟（到点弹横幅）；小组件等 iOS 专属能力以占位说明呈现；iOS 效果经 CI 构建 + TestFlight 安装到 iPhone 实机验收（Android 循环非必需）
- Q: iOS 打包验证按什么节奏触发 CI（Codemagic）构建？ → A: push 即构建 + 自动 TestFlight：每次推送触发 iOS 构建（含小组件扩展），构建通过后自动分发 TestFlight 供 iPhone 实机安装——「最新代码始终可装机、构建始终为绿」即打包验收标准

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 快速捕捉生活目标 (Priority: P1)

用户在状态好的时候（周末、假期、下班路上）萌生一个生活目标——"好好吃饭""每周锻炼 3 次""十一去旅行"。打开 App，通过预设模板或自定义，在 30 秒内把它变成一个具体、可衡量的目标。系统用 SMART 原则引导（如果目标太大或模糊，提示拆小或具体化），并限制活跃目标数量以保持聚焦。

**Why this priority**: 捕捉是一切的起点。没有低成本、高质量的录入，就没有后面的一切。它独立可用：即使只有这个功能，用户也获得了"把想法安放下来"的价值。

**Independent Test**: 可通过"空应用 → 选模板 → 生成目标"独立测试，交付价值：想法不再遗失。

**Acceptance Scenarios**:

1. **Given** 首次使用的空应用， **When** 用户选择预设模板"好好吃饭"并确认， **Then** 目标创建成功并出现在今日视图，全程不超过 30 秒
2. **Given** 用户自定义目标"每周锻炼 3 次"， **When** 设置频率为每周 3 次， **Then** 系统保存目标，且本周视图正确显示 0/3 的进度
3. **Given** 用户输入一个模糊目标"变得健康"， **When** 提交创建， **Then** 系统给出具体化建议（如拆为"每周运动 3 次"或"每天 23 点前睡"）供一键采用
4. **Given** 活跃目标已达 5 个上限， **When** 用户尝试新建第 6 个， **Then** 系统解释聚焦原则，并引导归档或完成一个现有目标后再创建

### User Story 2 - 今日一览与一键打卡（记分表） (Priority: P1)

忙碌工作日中的任意时刻，用户打开 App，首屏"今日"一屏展示全部活跃目标的今日状态——哪些已做、哪些还没做、连续坚持了几天。看到"今天还没锻炼"，晚上下班补上后点一下打卡，立即看到连击天数 +1 的反馈。全程 10 秒内完成，不需要翻页、不需要思考。

**Why this priority**: 这是产品的核心价值时刻——"在忙碌中看见自己的生活"。打卡闭环（看见 → 行动 → 反馈）就是最小可用产品；与 US1 合起来构成 MVP。

**Independent Test**: 预置 3 个目标后可独立测试"打开 → 逐一打卡 → 看到进度更新"闭环，交付价值：每天的生活被确认。

**Acceptance Scenarios**:

1. **Given** 用户有 3 个活跃习惯目标， **When** 任意一天打开应用， **Then** 首屏即今日视图，以"生活电量"为视觉核心，一屏内展示全部 3 个目标的今日待办与完成状态
2. **Given** 某目标今日进度为 1/3， **When** 用户点击其打卡按钮， **Then** 当日进度变为 2/3，连续天数/本周进度即时更新
3. **Given** 用户误打卡， **When** 当日内撤销， **Then** 该记录被撤销，连续天数与完成率随之回退
4. **Given** 用户处于无网络环境， **When** 打卡， **Then** 功能正常，数据保留在设备本地
5. **Given** 用户将小组件放置在手机桌面或锁屏， **When** 某目标今日尚未打卡， **Then** 小组件呈现各目标今日状态，点击该目标即完成一次打卡，全程无需打开应用
6. **Given** 今日全部目标已打卡完成， **When** 用户打开应用， **Then** 呈现正向的完成状态（而非空荡荡的待办列表）

### User Story 3 - 提醒：让目标主动找上门 (Priority: P2)

用户为目标设置提醒时间（如每天 12:00 提醒"好好吃饭"、20:00 提醒"锻炼"），或开启一条"今日生活概要"晨间提醒。加班忙碌时，目标通过通知主动浮现，而不是依赖用户记得打开 App。已完成的当日目标不再催促——提醒是温和的线索，不是打扰。

**Why this priority**: "被遗忘"是核心痛点，提醒是直接解法；但它依赖 US1/US2 先存在（有目标可提醒、有地方可打卡）。

**Independent Test**: 设置一条定时提醒后可独立验证到达时机与内容；交付价值：忙碌时目标不丢失。

**Acceptance Scenarios**:

1. **Given** 用户开启每日 8:00 的今日概要提醒， **When** 到达时间， **Then** 收到一条包含当日各目标状态的简短提醒
2. **Given** 用户为"锻炼"目标设置 20:00 提醒， **When** 该目标当日已打卡， **Then** 不再向用户发送该目标的催促提醒
3. **Given** 用户未授权通知权限， **When** 使用应用全部功能， **Then** 打卡、进度、回顾均正常可用，且应用在合适位置说明如何开启通知
4. **Given** 提醒时间处于系统勿扰/专注模式， **When** 时间到达， **Then** 系统按设备自身规则处理，应用不重复轰炸

---

### User Story 4 - 周回顾：规律的问责节奏 (Priority: P2)

每周一早晨，App 自动结算上一周（周一至周日）并生成一次轻量回顾：每个目标上周完成率与近几周趋势、一句反思引导（"这周哪天最难坚持？"）、下一步选择（继续 / 调低频率 / 暂停）。语气是教练式的、不指责的——完成率 40% 时得到的是"要不要调小一点？"而不是红色警告。用户用 2 分钟完成回顾，随晨间概要提醒触达，重新承诺新的一周。

**Why this priority**: 周回顾是 OKR/4DX 的"节奏"，让目标在更长的周期里保持活性、随生活调整；但没有日常打卡（US2）它无数据可回顾。

**Independent Test**: 使用满一周后可独立打开周回顾验证数据与流程；交付价值：目标被周期性重新审视而非一次设定后腐烂。

**Acceptance Scenarios**:

1. **Given** 用户已使用满一周且有多条打卡记录， **When** 打开周回顾， **Then** 看到每个目标本周完成率与趋势呈现
2. **Given** 某目标本周完成率低于 50%， **When** 周回顾呈现该目标， **Then** 系统提供调整选项（降低频率 / 暂停 / 拆小）且表达不含批评色彩
3. **Given** 用户在回顾中选择"下周继续"， **When** 新的一周开始， **Then** 目标保持活跃并进入新一轮周期统计
4. **Given** 某目标本周处于暂停状态， **When** 生成本周回顾， **Then** 该目标不计入完成率分母并标注"已暂停"

---

### User Story 5 - 里程碑目标：旅行与个人项目 (Priority: P2)

除了日常习惯，用户还有一些一次性的生活目标——"十一去厦门旅行""业余做一个自己的 App"。用户创建带截止日期的里程碑目标，可附步骤清单（订机票、查攻略……），随时查看倒计时与进度，让"想做的事"也有归属地和推进感。

**Why this priority**: 用户已确认习惯型与里程碑型两类目标在 v1 中并重支持——旅行、个人开发项目这类"想做的事"与日常习惯同样重要。排 P2 而非 P1，是因为其使用频率低于每日打卡、不构成最小闭环，但属于 v1 完整范围而非后续扩展。

**Independent Test**: 创建一个带截止日和步骤的里程碑目标后可独立验证倒计时与进度；交付价值：想做的事不因忙碌而搁浅。

**Acceptance Scenarios**:

1. **Given** 用户创建里程碑目标"十一去厦门"并设定截止日期， **When** 查看该目标， **Then** 显示距截止的倒计时
2. **Given** 里程碑含 3 个步骤且完成 1 个， **When** 查看该目标， **Then** 进度显示 1/3
3. **Given** 里程碑已过截止日期且未完成， **When** 查看， **Then** 温和提示顺延或关闭，不呈现失败惩罚

### Edge Cases

- 连续多日未打卡（加班/出差周）：连击中断的呈现必须温和，且提供两级保护入口——优先引导"忙碌模式"（降档不熄火），其次"暂停"，让用户主动选择而非默默弃用
- 深夜跨天打卡：23:59 与 00:01 的打卡按设备本地时区分别归属各自自然日
- 误打卡：当日打卡与补签均可撤销，撤销后统计即时回退
- 补签透明度：任意日期可补签以接住"做了但忘了记"的真实场景；补签记录标记"补"，周回顾如实呈现当期补签次数，避免连击与完成率被无感美化
- 当日次数已达目标次数：当日呈现完成态；超额打卡计入累计次数，当日完成度以 100% 封顶
- 目标达到上限后新建：聚焦引导（见 US1 场景 4）
- 全部完成后的空状态：呈现成就感的完成态，而非空白
- 删除/归档目标：历史打卡记录与已生成的周回顾保留，统计不回溯篡改
- "每周 3 次"类目标在周末结算时未达标：完成率如实呈现，但表达为下周调整建议
- 通知权限被系统级关闭或勿扰：功能降级可用，无报错
- 设备更换/重装：通过事先导出的备份文件导入恢复；导入时若本地已有数据，须提示冲突处理（覆盖或取消），不得静默合并

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 支持通过预设模板或自定义创建目标，字段包含：名称、类型（习惯型 / 里程碑型）、频率、图标与颜色，全程不超过 30 秒
- **FR-002**: 系统 MUST 支持习惯型目标设置频率（每天 N 次 / 每周 N 次 / 指定星期几；周周期统一定义为周一至周日），并据此自动计算"今日应做"（当日次数进度，如 2/3）与各周期完成率；对进行中目标修改频率时，新频率 MUST 自下一周期（下周一）生效，当前周期仍按原口径结算
- **FR-003**: 系统 MUST 提供首屏"今日视图"，一屏展示全部活跃习惯目标的今日状态与里程碑目标的进度概要；打卡、查看进度等日常操作不超过 2 次点击
- **FR-004**: 用户 MUST 能对当日目标一键打卡一次（当日计数 +1），并可撤销当日打卡；用户 MUST 能为过去任意日期补签打卡，补签记录 MUST 标记"补"、可撤销，并计入对应日期的统计
- **FR-005**: 系统 MUST 呈现进度可视化：连续天数（连击）、本周完成率、累计完成次数，且与打卡记录完全一致
- **FR-006**: 系统 MUST 支持按目标设置提醒时间，以及一条全局"今日概要"提醒；当日已完成的目标 MUST NOT 收到催促提醒
- **FR-007**: 系统 MUST 在通知权限未授权时保持全部核心功能可用（降级而非阻断）
- **FR-008**: 系统 MUST 于每周一早晨自动结算上一周（周一至周日）并生成周回顾：各目标 7 日完成率、趋势、反思引导，以及"继续 / 调频 / 暂停"的下一步选择，随当日晨间概要提醒用户参与；文案语气 MUST 保持教练式、非指责
- **FR-009**: 系统 MUST 支持目标暂停与恢复；暂停期间目标不出现在今日视图、不计入完成率分母
- **FR-010**: 系统 MUST 支持目标"达成关闭"与"归档"，并保留其历史记录用于回顾
- **FR-011**: 系统 MUST 将活跃目标数量上限设为 5（习惯型与里程碑型共享该上限），达到上限时给出聚焦引导
- **FR-012**: 系统 MUST 内置常见生活目标模板库（如：好好吃饭、规律运动、早睡、屏幕休息、个人项目时间）
- **FR-013**: 系统 MUST 支持里程碑型目标：截止日期、步骤清单、倒计时与进度呈现；里程碑型与习惯型目标在 v1 中同等完整支持
- **FR-014**: 系统 MUST 保障数据可用性：无账号即可使用、数据仅存储于设备本地、离线全功能可用，并在产品内提示定期手动备份
- **FR-015**: 系统 MUST 支持全量备份：一键将全部数据（目标、打卡记录、里程碑、提醒、周回顾）导出为单个备份文件，并支持从备份文件导入恢复；导入时若本地已有数据，MUST 提示冲突处理（覆盖本地或取消），不得静默合并
- **FR-016**: 系统 MUST 提供桌面小组件与锁屏小组件：以"生活电量"为视觉核心，展示今日各目标状态与进度，点击单个目标可直接完成一次打卡，无需打开应用主体
- **FR-017**: 系统 MUST 呈现"生活电量"：一个 0–100% 的聚合指标，由各活跃目标的完成度加权合成（派生计算，非独立存储），作为首屏与小组件的视觉核心；电量含义 MUST 取"提示照顾自己"而非"打分评判"的表达取向
- **FR-018**: 系统 MUST 提供"忙碌模式"：一键将所选（或全部）活跃习惯目标降至更低频率，降档当周即生效（显式豁免 FR-002 的"下一周期生效"规则），当周结算按降档口径计算；支持一键恢复原频率；降档期间今日视图与周回顾 MUST 如实标注"忙碌模式"

### Key Entities

- **目标 (Goal)**：用户的一个生活目标。属性：名称、类型（习惯型 / 里程碑型）、频率或截止日期、图标与颜色、状态（活跃 / 暂停 / 已归档 / 已达成）、创建时间
- **打卡记录 (CheckIn)**：某习惯型目标在某一自然日的一次完成（当日可多次，向当日目标次数累计）。属性：所属目标、日期、状态（有效 / 已撤销）
- **里程碑步骤 (MilestoneStep)**：里程碑目标下的一个可勾选步骤。属性：描述、完成状态
- **提醒 (Reminder)**：推动目标浮现的通知设置。属性：作用范围（某目标 / 全局概要）、时间、开关
- **周回顾 (WeeklyReview)**：一周的汇总快照。属性：周期、各目标完成率、用户反思笔记、下周决定（继续 / 调频 / 暂停）

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 新用户从打开应用到完成第一个目标创建（走模板路径）不超过 30 秒
- **SC-002**: 拥有 3 个活跃目标的用户，从打开应用到完成全部当日打卡不超过 10 秒
- **SC-003**: 所有统计呈现（连击、周完成率、累计次数）与原始打卡记录 100% 一致，可人工核对
- **SC-004**: 连续使用 4 周的用户中，60% 以上参与 3 次或更多次周回顾
- **SC-005**: 已完成当日全部目标的用户当天收到 0 条催促类提醒
- **SC-006**: 日常操作（打卡、查看进度、撤销）均在首屏 2 次点击内可达
- **SC-007**: 通过桌面/锁屏小组件查看今日状态并完成一次打卡不超过 5 秒，且无需打开应用主体
